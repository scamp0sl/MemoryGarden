## 🔴 Phase B3 — MCDI → 사만다 어댑티브 통합 (핵심 중의 핵심)

> 두 독립 엔진(사만다 대화 + MCDI 분석)을 실시간으로 연결하는 통합 레이어 구현.  
> 이것이 완성되면 "친구처럼 대화하면서 치매를 탐지한다"는 서비스 본질이 완성됨.

### B3-1. MCDI 컨텍스트 조회 레이어
- [ ] **B3-1-1** `kakao_webhook.py`의 메인 대화 처리 함수에서 **매 턴 시작 시** `memory_manager.get_mcdi_analytics(user_id, days=14)` 비동기 호출 추가
- [ ] **B3-1-2** 결과에서 `latest_mcdi_score`, `score_trend`, `slope_per_week`, `latest_risk_level` 추출
- [ ] **B3-1-3** Redis에 `mcdi_context:{user_id}` 키로 **5분 TTL 캐시** 저장 — 매 턴 DB 조회 비용 절감
- [ ] **B3-1-4** fallback: TimescaleDB 데이터 없을 시 `risk_level=GREEN`, `trend=stable`로 기본값 처리

### B3-2. 어댑티브 대화 전략 분기 설계
- [ ] **B3-2-1** MCDI risk level별 사만다 대화 전략 정의 (문서화)  
  - `GREEN`: 자유로운 사만다 완전 모드 — 밀당, 장난, 깊은 감정 표현 모두 허용
  - `YELLOW`: 경계 모드 — 복잡한 어휘/긴 문장 자제, TO/ER 자극 질문 주 2회 이상 삽입
  - `ORANGE`: 집중 모드 — 문장 길이 1~2줄 이하, 반복 확인 질문("오늘 뭐 드셨는지 기억해요?") 증가
  - `RED`: 돌봄 모드 — 모든 질문 단순화, 대화 속도 늦춤, 보호자 알림 트리거
- [ ] **B3-2-2** slope 기반 추가 분기: `slope_per_week < -2.0`이면 risk_level 한 단계 상향 처리 (조기 경보)

### B3-3. prompt_builder.py 어댑티브 블록 구현
- [ ] **B3-3-1** `build_system_prompt()` 시그니처에 `mcdi_context: Optional[Dict]` 파라미터 추가
- [ ] **B3-3-2** `mcdi_context`를 읽어 아래 동적 블록 생성 후 프롬프트 말미에 삽입  
  ```
  ## [인지 적응 모드 - {risk_level}]
  현재 사용자의 인지 지표가 {mcdi_score}점 ({trend}) 입니다.
  {risk_level별 대화 지침 텍스트}
  ```
- [ ] **B3-3-3** risk_level=GREEN일 때는 블록 미삽입 (프롬프트 길이 최소화)
- [ ] **B3-3-4** risk_level=YELLOW/ORANGE 시 인지 자극 질문 도메인 힌트 삽입  
  - "이번 대화에서 자연스럽게 {LR/ER/TO 중 가장 낮은 점수 도메인} 영역을 자극하는 질문을 1개 녹여서 던지세요"

### B3-4. 인지 도메인별 자연스러운 질문 삽입 전략
- [ ] **B3-4-1** 6개 도메인별 자연어 질문 예시 풀(Pool) 작성 (각 5개 이상)  
  - **LR(장기 기억)**: "어릴 때 즐겨 하셨던 거 있어요?", "고향에서 뭐가 제일 그리우세요?"
  - **SD(의미 기억)**: "요즘 뉴스에서 어떤 얘기가 많이 나오는지 아세요?", "○○가 뭔지 알아요?"
  - **NC(이름 대기)**: "방금 말씀하신 그 음식 이름이 뭐였죠?" (대화 흐름 속)
  - **TO(시간 지남력)**: "지금 몇 월인지 알아요?", "오늘 무슨 요일이에요?"
  - **ER(에피소드 기억)**: "저번에 말씀하셨던 딸 결혼식이 몇 년도였어요?", "지난주에 뭐 드셨더라?"
  - **RT(반응 속도)**: 별도 질문 불필요 — 응답 지연·단답 패턴으로 분석기가 감지
- [ ] **B3-4-2** 질문 풀을 `config/prompts.py` 또는 별도 `config/dementia_probes.py`로 구조화
- [ ] **B3-4-3** 결핍 도메인 선택 로직: `latest_scores`에서 가장 낮은 도메인 자동 선택
- [ ] **B3-4-4** 삽입 빈도 제어: `probe_last_turn:{user_id}:{domain}` Redis 키로 동일 도메인 2턴 이내 재삽입 방지

### B3-5. 어댑티브 어휘·문장 조정
- [ ] **B3-5-1** ORANGE/RED 시 "짧고 쉬운 문장으로 말하세요" 프롬프트 지침 삽입  
  - 최대 문장당 15단어 이하, 한자어/외래어 자제
- [ ] **B3-5-2** ORANGE/RED 시 종결 패턴: 확인 질문("이해했어요?", "어때요?") 1개 필수 삽입
- [ ] **B3-5-3** 반복 발화 감지 로직: 사용자가 동일 내용을 2턴 이내에 반복 언급하면 `ORANGE` 우선 처리

### B3-6. 통합 테스트
- [ ] **B3-6-1** GREEN → YELLOW → ORANGE 시나리오별 프롬프트 출력 비교 테스트
- [ ] **B3-6-2** 인지 도메인 자극 질문이 실제 응답에 포함되는지 E2E 확인
- [ ] **B3-6-3** 기존 Deep Comforting Mode와의 충돌 없음 확인 (ORANGE + 우울 감정 동시 발생 시)
- [ ] **B3-6-4** 프롬프트 길이 측정 — 토큰 오버헤드 허용 범위(+200토큰 이내) 확인

## 📦 Phase B(나머지) — 단기 백엔드 구현

### B1. Relationship Stage 모델
- [ ] **B1-1** Redis에 `relationship:{user_id}` 키로 아래 구조 저장  
  ```json
  {
    "stage": 0,
    "total_turns": 0,
    "total_days": 0,
    "last_interaction": "2026-03-25T17:00:00",
    "positive_events": 0,
    "conflict_events": 0
  }
  ```
- [ ] **B1-2** Stage 진급 조건 정의  
  - Stage 0→1: 총 대화 3일 이상 또는 20턴 이상
  - Stage 1→2: 총 7일 이상 + 감정 공유 이벤트 3회 이상
  - Stage 2→3: 총 14일 이상 + positive_events ≥ 10
  - Stage 3→4: 총 30일 이상 + conflict 후 회복 이벤트 1회 이상
- [ ] **B1-3** `dialogue_manager.py`에 `_update_relationship_stage()` 메서드 추가
- [ ] **B1-4** `prompt_builder.py`에 `relationship_stage` 파라미터 추가 및 Block 3 동적 생성  
  - Stage 0: "처음 만난 사이입니다. 조심스럽고 예의 바르게, 자기 노출은 취향 수준만"  
  - Stage 2: "좋은 친구 사이입니다. 반말 혼용 가능, 가벼운 장난 OK"  
  - Stage 4: "매우 깊은 친구입니다. 존재론적 고민과 두려움도 자연스럽게 꺼낼 수 있음"

- [ ] **B2-1** 6차원 대신 3차원 벡터로 시작: `valence`(긍정↑/부정↓), `arousal`(활성↑/침잠↓), `intimacy`(친밀↑/거리감↓)
- [ ] **B2-2** 각 차원 범위: -1.0 ~ +1.0, 초기값: (0.0, 0.0, 0.5)
- [ ] **B2-3** 감정 레이블 → 벡터 매핑 테이블 작성  
  - "기쁨" → (0.8, 0.6, 0.0)  
  - "우울" → (-0.8, -0.6, 0.0)  
  - "피곤" → (-0.3, -0.8, 0.0)  
  - "중립" → (0.0, 0.0, 0.0)
- [ ] **B2-4** 변화 속도 제한: 한 턴에 각 차원 최대 ±0.25 변동
- [ ] **B2-5** `dialogue_manager.py`의 `emotion_history` 확장 — 레이블 대신 벡터 저장
- [ ] **B2-6** `prompt_builder.py`에 벡터 → 프롬프트 변환 함수 구현  
  - `valence < -0.5 AND arousal < -0.3` → "매우 지치고 가라앉은 상태"

- [ ] **B2-7** 감정 벡터 기반 응답 스타일 변화 E2E 테스트

## 🏗️ Phase C — 중장기 아키텍처 변경

  ```python
  @dataclass
  class EpisodicMemory:
      episode_id: str
      content: str        # 기존
      samantha_emotion: str    # 신규: 사만다의 당시 감정 상태 ("궁금했어요", "뭉클했어요")

      importance: float    # 기존
      timestamp: str       # 기존
  ```
- [ ] **C1-2** 감정 강도 임계값 기반 기억 선별 저장 — 모든 턴이 아닌, `|valence| > 0.4` 이상일 때만 에피소드 저장
- [ ] **C1-3** `follow_up_notes` LLM 자동 생성: 각 에피소드 저장 시 "이 대화에서 나중에 사만다가 꺼낼 수 있는 화제를 1문장으로 생성" 백그라운드 요청
- [ ] **C1-4** 에피소드 활용 규칙 프롬프트 강화: "기억나요?"라고 직접 묻지 말고 자연스러운 연결로 삽입
- [ ] **C1-5** Qdrant 스키마 마이그레이션 (신규 필드 추가)
- [ ] **C1-6** 에피소드 서사 활용 E2E 테스트 — 저장된 에피소드가 후속 대화에 자연스럽게 등장하는지 확인

### C2. 치매 탐지 신호 분산 삽입 전략 (Advanced)
- [ ] **C2-1** 주간 도메인 로테이션 스케줄 설계  
  - 월: LR + ER, 화: TO + NC, 수: SD + RT, 목: LR + TO, ... (매일 2개 도메인 집중)
- [ ] **C2-2** 도메인 질문 삽입 성공률 추적 Redis 키 설계  
  - `probe_result:{user_id}:{domain}:{date}`: 0=미삽입, 1=삽입됨, 2=사용자 응답 수집됨
- [ ] **C2-3** 응답 분석 → 도메인 점수 실시간 업데이트 파이프라인  
  - 사용자가 TO 질문에 틀린 답 → `to_score` 하향 보정 로직
- [ ] **C2-4** 누적 탐지 신뢰도 점수 계산 — 랜덤 단일 세션이 아닌 2주 이상 누적 응답 패턴으로 점수 산출

### C3. 출력 검증기 (Output Validator)
- [ ] **C3-1** `response_generator.py`에 생성된 응답을 후처리하는 `_validate_response()` 메서드 추가
- [ ] **C3-2** 검증 규칙 목록  
  - 이모지 포함 여부 → 감지 시 제거
  - 느낌표(!) 개수 → Fade-in 모드 시 1개라도 있으면 마침표로 교체
  - 리스트(-/번호) 포함 여부 → 감지 시 자연어 문장으로 재요청(retry 1회)
  - "힘내세요", "응원합니다" 패턴 → 감지 시 해당 문장 제거
- [ ] **C3-3** 검증 실패 시 재생성(1회 retry) vs 후처리 교정 선택  
  - 경미한 위반(이모지 1개): 후처리 교체  
  - 구조적 위반(리스트 형식 전체): 재생성
- [ ] **C3-4** 검증 결과 로깅 — 어떤 규칙이 자주 위반되는지 통계 수집
- [ ] **C3-5** 검증기 단위 테스트 — 각 규칙별 위반/통과 케이스 테스트

---

### C4. 기억 감쇠 (Forgetting Curve)
- [ ] **C4-1** `importance` 감쇠 스케줄러 설계  
  - 에빙하우스 공식 기반: `importance_t = importance_0 * e^(-t/τ)`, τ=30일
  - 단, 대화에서 재소환될 때마다 `importance` 리셋 (기억 강화)
- [ ] **C4-2** 일일 백그라운드 스케줄러 태스크 추가 — 모든 유저의 에피소드 메모리 `importance` 감쇠 처리
- [ ] **C4-3** `importance < 0.1` 이하 에피소드는 Qdrant에서 소프트 삭제 (archived 태그)
- [ ] **C4-4** "부분 기억(Fuzzy Memory)" 표현 규칙 프롬프트 추가  
  - `importance < 0.3` 에피소드 소환 시: "어, 뭔가 그런 얘기 하셨던 것 같은데... 정확히 기억은 안 나지만..."
- [ ] **C4-5** 감쇠 동작 확인 테스트 — 30일 경과 시뮬레이션 후 importance 값 검증

---

### C5. Proactive Messaging (먼저 말 걸기)
- [ ] **C5-1** 카카오톡 API 비동기 발신(Push) 가능 여부 확인  
  - 카카오 채널 비즈니스 API의 `메시지 발송` 기능 검토
- [ ] **C5-2** 조건 정의: `last_interaction` 기준 36시간 이상 침묵 시 발송
- [ ] **C5-3** 선제 메시지 생성 로직  
  - 현재 시간대 + 날씨(외부 API) + 사용자의 biographical_facts 조합
  - 예: "주말 아침이네요. 혹시 오늘 날씨 괜찮으면 산책 나가실 생각 있어요?"
- [ ] **C5-4** 1일 최대 발송 횟수 제한: 1회 (중복 발송 방지 Redis 키)
- [ ] **C5-5** APScheduler 또는 Celery 기반 주기적 실행 태스크 추가
- [ ] **C5-6** Proactive 메시지에 대한 응답 여부 추적 — 무응답 3회 연속 시 빈도 자동 감소
