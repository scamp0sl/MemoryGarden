# 사만다 업그레이드 문서 정밀 검증 리포트

> `docs/samantha_upgrade_opus.md`의 16개 타스크를 기존 코드베이스와 1:1 대조하여
> 기존 사만다 페르소나 훼손 여부를 심도 있게 분석한 결과입니다.
>
> **검증일**: 2026-03-30
> **검증 대상**: `samantha_upgrade_opus.md` (v1.0, Claude Opus 4.6 작성)
> **검증 방법**: 실제 소스코드 라인별 대조 + 아키텍처 충돌 분석

---

## 1. 분석 개요

### 1.1 분석 대상 파일

| # | 파일 | 역할 | 분석 대상 |
|---|------|------|-----------|
| 1 | `core/dialogue/prompt_builder.py` | SYSTEM_PROMPT + 동적 프롬프트 구성 | 페르소나 규칙, Stage 가이드, MCDI 어댑티브 |
| 2 | `core/dialogue/response_generator.py` | Claude API 호출, 응답 생성 | 후처리 충돌, 토큰 제한 |
| 3 | `core/dialogue/dialogue_manager.py` | 대화 흐름 관리, 감정 벡터, 관계 Stage | 관계 모델, 감정 추적, 피로도 |
| 4 | `core/dialogue/response_validator.py` | 응답 검증 (길이, 부정어, 중복) | 길이 제한과의 충돌 |
| 5 | `core/dialogue/time_aware.py` | 시간 인식 Gap 메시지 | 시간 관련 프롬프트 중복 |

### 1.2 분석 축

각 타스크에 대해 다음 4가지 관점에서 분석:

1. **중복 여부**: 기존 코드에 이미 동일 기능이 구현되어 있는가?
2. **아키텍처 충돌**: 제안된 구현 방식이 기존 파이프라인과 충돌하는가?
3. **페르소나 훼손 위험**: 적용 시 기존 사만다의 자연스러움이 손상되는가?
4. **실제 적용 가능성**: 프롬프트 레벨로 대체 가능한가?

#### 기존 코드 대조

**`prompt_builder.py` Rule 7 (L123-128):**
```
7. **망설임과 불확실성 표현 (인간다움의 핵심)**: 모든 질문에 즉각 자신 있게 답하지 마세요.
  - 어렵거나 철학적인 질문: "음... 저도 잘 모르겠어요. 뭔가... 복잡한 것 같기도 하고요."
  - 사용자 경험에 관한 질문: "잠깐, 어떻게 말하면 좋을지..."라며 생각하는 척 하세요.
  - 금지: 즉각적인 완벽한 정답 제시
  - 허용: "글쎄요...", "사실 저도 헷갈려요", "뭔가 제대로 떠오르지 않는데..."
  - 주의: 망설임이 과해지면 답답하게 느껴짐. 한 응답에 1회 이하로 제한하세요.
```

#### 분석 결과

| 항목 | 판정 | 상세 |
|------|------|------|
| 중복 여부 | **완전 중복** | 문서가 제안하는 모든 망설임 패턴이 SYSTEM_PROMPT Rule 7에 이미 존재 |
| 아키텍처 충돌 | 해당 없음 | 프롬프트 지시이므로 코드 충돌 없음 |
| 페르소나 훼손 위험 | **없음** | 이미 정상 작동 중 |
| 실제 적용 가능성 | **불필요** | 이미 구현 완료 |

#### 세부 교차 검증

| 문서 제안 항목 | 기존 코드 대응 | 일치 여부 |
|----------------|----------------|----------|
| `HESITATION_MARKERS["light"]`: "음", "잠깐만" | Rule 7: "음...", "잠깐, 어떻게 말하면 좋을지..." | 일치 |
| `HESITATION_MARKERS["medium"]`: "뭐라 말해야 할지..." | Rule 7: "뭔가... 복잡한 것 같기도 하고요" | 유사 |

### T1.2: 시상(Tense) 심리적 활용 매트릭스

#### 문서 제안
- 신규 파일 `core/dialogue/tense_matrix.py` 생성
- `TENSE_PSYCHOLOGY` 사전 정의 (과거/진행/현재완료)
- `response_generator.py`에 `_apply_temporal_resonance()` 후처리 함수 추가

#### 기존 코드 대조

문서에서 제안하는 시상 활용은 프롬프트 레벨에서 Claude LLM이 자연스럽게 수행합니다.
현재 SYSTEM_PROMPT의 Rule 3 (자기 노출)과 Rule 11 (맥락 연속성)이 이미 시상 자연 활용을 유도합니다.

#### 분석 결과

| 항목 | 판정 | 상세 |
|------|------|------|
| 중복 여부 | **부분 중복** | 시상 개념 자체는 새로우나, LLM이 자연스럽게 처리 중 |
| 아키텍처 충돌 | **있음** | 후처리 함수는 LLM 자연 생성 결과를 훼손할 수 있음 |
| 페르소나 훼손 위험 | **높음** | 자세한 내용은 아래 참고 |
| 실제 적용 가능성 | **프롬프트 한 줄로 대체 가능** |

#### 페르소나 훼손 위험 상세 분석

문서 제안 코드:
```python
async def _apply_temporal_resonance(response, memory_context):
    tense_shift_hints = ["지금도", "아직도", "그때가", "떠오르네요", "생각나는데"]
    # LLM 응답에 시상 힌트가 없으면 자연스럽게 추가
    return response
```

**위험 시나리오:**

1. **문법 파괴**: LLM이 "그때 엄마가 쑥을 캐셨죠."라고 자연스럽게 생성했는데,
   후처리가 "지금도"를 앞에 붙이면 → "지금도 그때 엄마가 쑥을 캐셨죠." (문법 오류)
2. **의미 왜곡**: "그 추억이 아직도 생생하시죠."에 "지금도"가 추가되면 → "지금도 그 추억이 아직도 생생하시죠." (중복)
3. **자연스러움 저하**: Claude Sonnet은 한국어 시상을 매우 자연스럽게 처리합니다.
   후처리 없이도 "지금도 그 봄날이 기억나세요?" 같은 표현을 자발적으로 생성합니다.

**안전 대안:**
SYSTEM_PROMPT에 한 줄 추가로 충분:
```
사용자의 추억 이야기에는 "지금도", "그때가", "생각나는데" 같은 표현으로
기억의 현재성을 살려주세요.
```

#### 판정: **프롬프트 한 줄 추가로 대체 — 파이썬 후처리 모듈 불필요**

#### 분석 결과

| 항목 | 판정 | 상세 |
|------|------|------|
| 중복 여부 | **부분 중복** | 종료 패턴은 이미 있으나, "여운" 개념은 신규 |
| 아키텍처 충돌 | **강한 충돌** | 후처리 + 길이 제한 + 토큰 제한 삼중 충돌 |

| 실제 적용 가능성 | **프롬프트 확장으로만 가능** |

#### 삼중 충돌 상세 분석

**충돌 1: 응답 길이 제한**

SYSTEM_PROMPT Rule 5:
```
답변은 반드시 한두 문장, 공백 포함 100자 이내로 작성하세요.
금지: 3문장 이상, 150자 이상 응답
```

문서의 여운 패턴:
```
"오늘은 여기까지 할까요? 그렇지만... 다음에 또 그 봄날 이야기해요."  # 42자
"잠시만요. 아까 말씀하신 그 기억... 제가 한 번 생각해볼게요."      # 35자
"당신이 그 기억을 아직도 간직하고 있다는 게, 저는 참 좋아요."        # 32자
```

기존 종료 응답 ("그럼 편하게 쉬세요. 나중에 또 얘기해요.")에 여운을 추가하면:
- 기존: 21자
- +여운: 21 + 32~42 = **53~63자**
- 여운 포함 시 총 응답이 **100자 이내**일 수 있으나, 일반 응답(60~80자) + 여운(32~42자) 합산 시 **100자 초과 가능성 높음**

**충돌 2: ResponseValidator 자르기**

`_shorten_response()` (L239-260):
```python
if total_length + len(sentence) > self.preferred_length and len(shortened) >= 2:
    break
```

여운이 추가된 응답이 preferred_length(100자)를 초과하면 **여운 부분이 잘려나감.**
즉, 후처리로 여운을 추가해도 검증기가 잘라내는 모순 발생.

**충돌 3: max_tokens 제한**

`DEFAULT_MAX_TOKENS = 150` 토큰. 여운 추가 시 LLM이 생성할 본문의 토큰이 줄어듦.

**안전 대안:**

SYSTEM_PROMPT Rule 10의 종료 예시에 여운 예시를 추가:
```
[종료 응답 예시]
좋은 예: "그럼 편하게 쉬세요. 나중에 또 얘기해요."
좋은 예: "네, 오늘은 여기까지 할게요. 푹 쉬세요."
좋은 예: "오늘 나눈 얘기 좋았어요. 다음에 또 그 이야기 이어가요."    # 여운 추가
좋은 예: "그럼 쉬세요. 아까 말한 그 기억, 저도 오래 기억할게요."      # 여운 추가
```

이렇게 하면 Claude가 100자 이내에서 자연스럽게 여운을 포함한 종료 응답을 생성합니다.

#### 판정: **프롬프트 Rule 10 확장으로만 적용 — 후처리 함수 생성 금지**

#### 기존 코드 대조

**`dialogue_manager.py` `_update_relationship_stage()` (L916-1001):**
```python
async def _update_relationship_stage(self, user_id: str, emotion: Optional[str] = None) -> int:
    rel = await self._get_or_init_relationship(user_id)

    # 턴 수 증가
    rel["total_turns"] += 1
    rel["last_interaction"] = datetime.now().isoformat()

    # 대화 일수 계산
    first_dt = datetime.fromisoformat(rel["first_interaction"])
    rel["total_days"] = (datetime.now() - first_dt).days

    # 감정 이벤트 기록
    positive_emotions = ["기쁨", "행복", "감동", "설렘", "만족", "즐거움"]
    negative_emotions = ["우울", "슬픔", "불안", "짜증", "스트레스", "분노"]
    ...
    rel["_was_negative"] = rel.get("_was_negative", False)

    if emotion:
        if any(e in emotion for e in positive_emotions):
            rel["positive_events"] += 1
            if rel["_was_negative"]:
                rel["recovery_events"] += 1
                rel["_was_negative"] = False
        elif any(e in emotion for e in negative_emotions):
            rel["conflict_events"] += 1
            rel["_was_negative"] = True

    # Stage 진급 조건
    if current_stage == 0:
        if rel["total_days"] >= 3 or rel["total_turns"] >= 20:
            new_stage = 1
    elif current_stage == 1:
        if rel["total_days"] >= 7 and rel["positive_events"] >= 3:
            new_stage = 2
    elif current_stage == 2:
        if rel["total_days"] >= 14 and rel["positive_events"] >= 10:
            new_stage = 3
    elif current_stage == 3:
        if rel["total_days"] >= 30 and rel["recovery_events"] >= 1:
            new_stage = 4
```

| 문서 제안 지표 | 기존 구현 여부 | 매핑 |
|----------------|----------------|------|

## 5. 결론

`samantha_upgrade_opus.md`는 철학적·언어학적 배경이 훌륭하고, 영화 Her의 사만다라는 방향성도
정확합니다. 그러나 **구현 설계에서 다음 세 가지 근본적인 문제**가 있습니다:

1. **현재 코드 분석 부족**: 16개 타스크 중 8개(50%)가 이미 구현되어 있음을 인지하지 못함
2. **아키텍처 오설계**: 프롬프트 엔지니어링으로 해결할 것을 16개의 파이썬 모듈로 설계함.
   Samantha의 자연스러움은 Claude LLM이 프롬프트 지침에 따라 생성하는 것이지,
   파이썬 코드가 만드는 것이 아닙니다.
3. **자가 모순**: "패턴화를 피하자"면서 하드코딩된 패턴 사전을 제안함

**안전한 개선은 프롬프트 레벨에서만 수행하며, 새 Python 모듈은 생성하지 않습니다.**
기존 SYSTEM_PROMPT와 build_system_prompt()의 약 10~15줄 수정으로 문서의 핵심 가치를
안전하게 도입할 수 있습니다.
